# Watch / iPad Platform Boundaries

## Purpose and status

The project includes a local `FactoryToolsCore` static framework used by the universal iPhone/iPad app, app-independent Core tests, and the Apple Watch app. A separate macOS Core test target remains available. Core has iOS, iOS Simulator, macOS, and watchOS build slices. The iPhone app is authoritative for count state; Watch sends versioned commands over WatchConnectivity, while iPad uses paired local Network.framework transport. The project uses local storage, no third-party packages, no internet APIs, no external network services, and no paid services.

## Privacy manifest audit

The universal iPhone/iPad app and the Apple Watch app each use Swift `ContinuousClock` for their local Cycle Time stopwatch. The same `PrivacyInfo.xcprivacy` declares `NSPrivacyAccessedAPICategorySystemBootTime` with reason `35F9.1` in both app bundles, matching Apple's approved purpose for elapsed-time measurement and timers. The Watch sends the resulting in-app Cycle Time interval to its paired iPhone; it does not transmit raw system boot time. Current source inspection found no direct UserDefaults, file-timestamp, disk-space, active-keyboard, or raw system-uptime API use, and no third-party SDKs; therefore the manifest makes no collection or tracking declarations and is not included in the shared Core framework. This is a source audit, not the App Store Connect privacy questionnaire; the publisher must still answer that separately from the shipped product and distribution configuration.

Apple references: [Privacy manifest files](https://developer.apple.com/documentation/bundleresources/privacy-manifest-files), [required reason API categories and reasons](https://developer.apple.com/documentation/bundleresources/app-privacy-configuration/nsprivacyaccessedapitypes/nsprivacyaccessedapitype), and [`ContinuousClock`](https://developer.apple.com/documentation/swift/continuousclock).

## Pairing-secret scene redaction

The iPhone pairing secret is stored in the Keychain and used as the TLS-PSK input; source review found no pairing-secret logging. Settings marks the displayed code and both code-entry fields as privacy-sensitive and applies SwiftUI's `.privacy` redaction reason whenever the Settings scene is inactive or `EnvironmentValues.isSceneCaptured` reports recording, mirroring, or remote capture. The policy is scene-scoped, so an inactive or captured iPad window does not rely on another window's display state. This obscures the SwiftUI fields during those states; it does not block a person from deliberately copying or sharing the code. Apple describes the scene-capture environment value and selective redaction in [Protecting sensitive content when screen sharing and remote control are active](https://developer.apple.com/documentation/swiftui/protecting-sensitive-content-when-screen-sharing). The source regression covers active/visible, inactive/redacted, captured/redacted, and both conditions together. Confirm the actual app-switcher and capture behavior on the signed release build before distribution.

The command value is portable: it has a schema version, stable command ID, session ID, operation, and creation time. Operations include counter changes and an idempotent target update; target changes are stored as command receipts and do not create count events. Shared Core provides a schema-versioned Codable FIFO outbox, an atomic JSON file store, and a bounded exponential retry schedule. The Watch and iPad resend the head after reconnect/relaunch and remove it only after a matching acknowledgement. iPad stores one queue per SHA-256 pairing-secret fingerprint so changing peers cannot send the previous peer's pending actions to the new phone; restoring a previous pairing secret restores its queue. The previous unscoped iPad queue is displayed as unassigned and is not sent until the user confirms reassignment; scoped data is saved before the legacy file is removed, and malformed/conflicting legacy queues remain untouched.

## Current target boundaries

### `FactoryToolsCore` (Foundation only)

The current local static framework already contains these shared source types:

- `ToolID`, card-size identifiers, `ToolCapabilities` for Watch support and supported sizes, and `ToolSessionPolicy` for production/defect session ownership and initial targets.
- `CounterCommand`, its operation enum, stable event-kind identifiers, and timestamp-range validation.
- Count-delta bounds, history ordering, latest-Undoable selection, progress math, and other deterministic calculations.
- Codable command protocol types and their schema validation.

The framework is linked by the iPhone app, Watch app, and test targets. `FactoryToolsCoreTests` is an app-independent macOS test bundle that imports the public Core module. Its contracts include every known counter operation, Watch catalog validation, retry delay bounds, FIFO acknowledgement, timestamp-range endpoints, overflow-safe box capacity, and unit-conversion round trips. Project settings include watchOS and Watch Simulator slices; native Apple-platform compilation remains unverified here.

Core must not import SwiftUI, SwiftData, UIKit, WatchKit, or read the user's locale. Keep localized titles, category names, default session names, and display formatting in each app's presentation layer. Cross-platform tool capability and session rules stay canonical in Core; the app Registry adds availability, typed iPhone routes, and localization. Version 1 Watch layout is Watch-native: iPhone S/M/L sizes and the iPhone dashboard's cross-tool arrangement do not transfer. Watch uses fixed compact sections; the relative order within counter and progress sections follows the corresponding iPhone cards. There are no Watch-specific size controls.

### `FactoryToolsPersistence` (Apple persistence layer)

When multiple targets need the same durable entities, move SwiftData models and transaction services together so there is one definition of IDs, sessions, events, receipts, and backup compatibility. It may depend on `FactoryToolsCore`; Core must not depend on it. Keep schema versioning and backup migrations explicit when model fields or payloads change.

The iPhone container now uses `FactoryToolsSchemaV1` with all eight persisted models and a `SchemaMigrationPlan` baseline. This is the first-release schema inventory, not evidence that earlier unversioned development stores migrate. Before changing a persisted property or model inventory after release, add a new `VersionedSchema`, declare its migration stage, and verify an old-store fixture on Apple platforms. The initial one-version plan intentionally has no stages.

### App targets

- iPhone owns home creation, naming, layout, language/theme preferences, and the canonical local history.
- Watch presents only Core-supported tools whose card has `showsOnWatch == true`, exposed through the app Registry. Counter controls use the counter catalog; Cycle Time exposes the selected home and sends recorded one-unit samples to the iPhone; Pro Production Progress uses an additive, read-only progress snapshot. The iPhone includes those progress snapshots only for the selected home, enabled cards, and an active Pro entitlement. Core capability remains an upper bound; the saved preference is not proof that a tool supports Watch. Version 1 Watch layout uses compact fixed sections rather than iPhone S/M/L sizes or the iPhone dashboard's cross-tool order; relative card order is retained within the counter and progress sections.
- iPad runs the same universal target with an adapted larger layout. The iPhone remains the count authority. iPad has a separate local store for the shared app's non-remote data, but remote counter actions are command messages and never write to a competing count history. The iPad dashboard appears from the home toolbar; pairing controls live in Settings.

## Current command-delivery contract

The iPhone is the canonical writer for count history. Watch and iPad send counter commands; they do not independently merge count totals. Both keep a durable FIFO outbox until the iPhone acknowledges each counter command. The iPhone applies counter commands through the same service as local actions and returns one of `applied`, `alreadyApplied`, `noChange`, or `rejected` for current operations. Watch Cycle Time uses its own durable FIFO of stable-ID capture commands, saved by the iPhone as `CycleTimeSample` records. Retries preserve each command ID. The Watch command path remains restricted to visible supported tools on a home; the iPad catalog shows the selected home, while its processor also accepts an already-queued counter command for any still-existing, correctly linked counter session; this preserves offline actions if the iPhone changes home before reconnect. `staleUndo` remains reserved for a future Watch Undo acknowledgement flow.

The existing command envelope carries a unique ID and an explicit Undo event ID. `CounterCommandOutbox` stores commands in insertion order, treats an identical re-enqueue as a no-op, and rejects reuse of an ID with changed command content. Normal acknowledgements remove only the current head; explicit session cleanup can discard every queued command for a session after the iPhone confirms that session is no longer available, preserving all other commands in their original order. Codable restoration rejects duplicate IDs and unsupported schema versions. `CounterCommandOutboxFileStore` atomically replaces a JSON file and does not silently recreate a queue when the saved file is malformed. `CounterCommandAcknowledgement` carries the processed command ID and one of five versioned, locale-independent status values; unknown versions and statuses are rejected. The iPhone assigns event sequence numbers and updates `currentCount`; Watch displays the last iPhone-authoritative snapshot and shows pending commands separately. A per-head in-flight guard prevents parallel sends. Both transports use the shared Core response validator: all acknowledgements must match the sent command, any supplied snapshot must validate and match its session, and `applied`, `alreadyApplied`, `noChange`, or `staleUndo` require an authoritative snapshot before the outbox advances. Only a matching `rejected` response without a snapshot indicates that the session is unavailable; the Watch and iPad then discard all queued commands for that session and retain every other command in FIFO order. Rejections with a valid snapshot acknowledge only the current command, leaving later work for the still-available session intact. The iPad applies enqueues and responses to a candidate queue, writes that queue first, and only then publishes it in memory, updates the visible pending count, and sends its next command; a storage failure leaves the prior queue available and schedules a reconnect retry of its head command. Malformed or incomplete responses leave the command queued; Watch retries with capped exponential backoff and a 15-second per-attempt timeout, ignoring replies from expired attempts, while iPad reconnects after its 15-second response timeout. Connection and listener events carry generation IDs so delayed callbacks from an older connection cannot change the current peer state. The frame decoder bounds its buffered frame while accepting a large TCP read containing multiple complete frames. The Watch transport, removal of unavailable sessions, and localized refresh recovery are implemented.

### Required behavior

1. A command with an already-seen ID and identical payload is idempotent and returns its original outcome.
2. Reusing an ID with a different payload is an identifier conflict, even when the session ID matches.
3. A command for a missing/deleted session is rejected; callers must resolve the persisted session by ID before applying it.
4. Undo carries the event ID observed by the sender. If it is no longer the latest undoable event, reject it as stale and synchronize current history; do not silently undo a different event.
5. Acknowledged no-op commands remain deduplicated, as current `CounterCommandReceipt` already supports.
6. Deleting a home/session invalidates commands addressed to that session ID. Home deletion removes its sessions, events, receipts, and cards transactionally. A late command resolves by its persisted session ID, so it is rejected without a snapshot when that session no longer exists; the peer outbox then discards commands for that unavailable session while preserving other sessions. Recreating a home with the same display name creates new home/session IDs, and backup import remaps IDs. The regression test `testLatePeerCommandForDeletedHomeCannotApplyToSameNamedReplacement` covers delete, same-name recreation, and late delivery. V1 therefore does not need a tombstone or generation marker; revisit this if a future restore/replacement flow intentionally reuses deleted IDs.

### Command replay and compatibility

New `CountEvent` and `CounterCommandReceipt` records persist a canonical payload fingerprint derived from the command schema, operation (including Quick Add amount or Undo target), and creation timestamp. `CounterService.apply` accepts an exact same-ID/same-session/same-payload replay and reports an identifier conflict when a stored fingerprint differs. The fingerprint intentionally excludes session ID because additive import remaps that ID; the service compares session identity separately. Its persisted form validates the schema number, operation identifier, and canonical hexadecimal timestamp bit pattern. For known operations, backup validation also verifies that the signature agrees with the event timestamp, kind, delta, and Undo target. An ID appearing in both the event and receipt collections is rejected, and local replay handling treats that cross-type collision as corruption.

The new fields are optional so existing SwiftData rows can be opened through the additive model evolution path. Backups now export Version 4, and Versions 1–3 remain readable. Legacy events and receipts without a fingerprint retain the prior ID/session replay behavior because the original command payload is unavailable; these records are not retroactively fingerprinted. Version 4 import/export preserves signatures while remapping record and session IDs. The native SwiftData migration behavior still needs confirmation in an Apple build environment before shipping.

## iPad peer transport direction

The implementation uses a direct Apple local peer connection with Network.framework Bonjour discovery, a shared random 256-bit pairing secret stored in each device's Keychain, TLS 1.2 with the explicit `TLS_PSK_WITH_AES_256_GCM_SHA384` cipher suite, and the Core `CounterPeerMessage` envelope. The iPhone advertises only on iPhone while the app is active; iPad browses and sends the existing `CounterCommand` values through its persistent FIFO outbox. The iPad screen supports +1, -1, fixed/custom Quick Add, Undo, target changes, and confirmed reset. Outboxes are scoped by a SHA-256 fingerprint of the pairing secret. A legacy queue with no known peer is held for explicit reassignment, so peer changes do not redirect old commands. No app-operated cloud sync/backend or third-party endpoint is involved in this peer transport; Apple may separately include local app data in OS-managed device backups. Apple marks Multipeer Connectivity deprecated and directs new peer-to-peer work to Network.framework ([TN3151](https://developer.apple.com/documentation/technotes/tn3151-choosing-the-right-networking-api?changes=_1_2), [TN3213](https://developer.apple.com/documentation/technotes/tn3213-moving-from-multipeer-connectivity-to-network-framework?language=obj_5)); the classic `NWBrowser`/`NWListener`/`NWConnection` APIs support the project's iOS 17 baseline. Apple's Network.framework TLS-PSK support is limited to the classic APIs and TLS 1.2, so both peers are pinned to TLS 1.2 ([TN3213](https://developer.apple.com/documentation/technotes/tn3213-moving-from-multipeer-connectivity-to-network-framework?language=obj_5)). Bonjour use requires local-network permission text and service declarations ([TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy?changes=__3)); peer-to-peer Wi-Fi is enabled through Network framework parameters ([NWParameters.includePeerToPeer](https://developer.apple.com/documentation/network/nwparameters/includepeertopeer?changes=_5)). Connections may pause when an app backgrounds, so the durable queue and active-app reconnect flow remain necessary. Source and Windows static validation are complete; native compilation and runtime checks remain unverified.

## Version 1 transport scope

- Watch uses immediate foreground messaging with durable offline queues and capped retry. The counter and Cycle Time outboxes each hold up to 5,000 pending commands and each persisted JSON file is capped at 4 MiB; loading checks file size before and after reading, and oversized files are left untouched. Background delivery is a later enhancement; queued commands do not expire by time. At capacity, an outbox preserves its existing FIFO and rejects new actions until acknowledgements free a slot.
- Local retention policy: records are not aged out. Pairing keys remain until explicitly replaced or removed; queued peer commands remain durable until acknowledged or rejected for an unavailable session; processed receipts follow their local counter history. This preserves offline recovery and command idempotency without silently deleting user data.
- One peer connection is active or pending per iPhone at a time. The listener rejects additional incoming connections while that slot is occupied, preserving the current iPad connection; the UI reports “connecting” until the TLS-PSK connection is ready. Multiple authorized iPads are outside the initial scope.

## Implementation sequence

1. Core source boundary, watchOS build settings, Watch target, and immediate command path are implemented. Core contract source coverage includes stable acknowledgement values, FIFO restoration, exact retries, ID collisions, bounded retry delays, ordered acknowledgements, atomic file persistence, and malformed-file preservation; native XCTest execution is not verified in this workspace.
2. Keep the current persistence ownership unless a later product or platform requirement needs a shared Apple target. If that architecture changes, preserve the existing on-device store URL and prove old-store migration before shipping.
3. Watch foreground lifecycle recovery is implemented: the durable queue reloads on launch/resume, refreshes the catalog on activation/reachability changes, ignores stale attempt replies, and offers non-destructive storage retry. Background delivery remains a possible later enhancement; queued commands have no time-based expiration.
4. Source-level command delivery and retry regression coverage is in place. Apple-platform runtime verification remains a release gate, not a Windows source-check result.

## Apple Watch counter implementation

- The Watch app has a local persistent FIFO for counter commands and a separate Cycle Time timer/outbox. It queues +1, -1, and +5 counter commands while offline, then resends the unchanged head through `WCSession.sendMessage` when the iPhone is reachable. It removes an item only after the matching command ID is acknowledged and the acknowledgement is persisted. The Cycle Time outbox also preserves its timer's home binding and elapsed time across relaunches.
- The iPhone processes commands through the same `CounterService` used by its own UI. Event IDs are command IDs, so retries do not duplicate count changes. Watch count displays remain at the last iPhone-authoritative snapshot while commands are pending; the Watch shows the pending count separately.
- Counter catalog publication is limited to Production Counter and Defect Counter sessions on the selected home whose cards are marked for Watch display. A separate read-only Production Progress section is included only with Pro, and only for Watch-enabled progress cards linked to the selected home's production session. Commands for removed, hidden, unsupported, or deleted sessions are rejected.
- The selected home's Cycle Time card is included in the catalog when **Show on Apple Watch** is enabled. The Watch saves a stopwatch's active/paused state locally and sends completed one-unit measurements through an independent durable FIFO. The iPhone validates that the home remains accessible and the Cycle Time card remains Watch-enabled, then inserts the `CycleTimeSample` with the command ID as its unique ID. Retried delivery detects the existing identical sample and acknowledges it without duplication.
- The iPhone republishes its catalog after counter/target changes, selected-home changes, home renames/deletion, and card add/remove/reorder, and only when a Watch is paired and the Watch app is installed. Saved counter changes publish through the shared counter service, so command handlers do not build a second catalog after replying. The Watch requests a fresh catalog on activation, reachability restoration, and app resume.
- This initial Watch transport uses immediate messages while the paired iPhone is reachable, with capped exponential retry for transient failures or invalid responses. Background delivery and Undo from Watch remain future decisions. A Watch action that becomes stale is currently returned as a rejected command; a distinct stale-Undo acknowledgement status is reserved for a future Watch Undo flow.
- The Watch target and source are included in the Xcode project and scheme. Windows static validation checks project wiring and source structure, but cannot compile Swift or execute Apple-platform tests.
