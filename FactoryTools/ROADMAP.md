# Factory Tools Roadmap

This roadmap records the agreed direction and current implementation state. Future feature details that have not been approved are intentionally not treated as Version 1 requirements.

## Product direction

- iPhone is the first complete app and the primary place to configure the home.
- Apple Watch is the later shop-floor companion.
- iPad uses the same universal iPhone/iPad app; iPhone remains the count authority and iPad sends counter commands rather than writing a competing history.
- Keep tool IDs and domain behavior independent of display language and SwiftUI views. The local iOS `FactoryToolsCore` framework is now the first shared source boundary; [PLATFORM_BOUNDARIES.md](PLATFORM_BOUNDARIES.md) documents its current contents and the Version 1 Watch/iPad transport boundaries.
- Use Apple platform frameworks and local storage. Keep external packages, internet APIs/services, cloud services, and paid development services out of the project; the iPad path uses direct local peer-to-peer transport.
- The first-release commercial model is Free plus a one-time Pro purchase. The boundary and StoreKit behavior are recorded in [PRODUCT_DECISIONS.md](PRODUCT_DECISIONS.md); the one-time StoreKit purchase and entitlement flow is implemented; Japan's ¥980 base storefront is confirmed and awaits App Store Connect setup, while `factorytools.pro.lifetime` remains the selected product ID candidate. Version 1 is intended for all currently available App Store territories where Apple permits distribution, with English primary metadata and Japanese localization.

When an iPad has pending counter commands, Settings loads the queue for the current pairing code before allowing a code switch. It asks for confirmation and explains that pending commands remain attached to the old code; re-entering that code resumes delivery, while a new code never inherits the queue.

Recent peer-transport reliability refinement: a matching `rejected` acknowledgement without a session snapshot now uses one shared Core contract on both Watch and iPad. Each sender discards only queued commands for the unavailable session, preserving unrelated commands and their FIFO order; a rejection with a valid snapshot removes only the acknowledged head.

StoreKit cold-launch reliability: Watch catalog publication and command handling, plus the iPhone's iPad-command authority startup, now wait for the initial entitlement lookup to resolve. This prevents a returning Pro user's queued companion actions from being rejected as Free during the brief launch window; an unresolved Watch request receives a retry response, and queued commands remain in their durable outboxes.

The iPad now ignores a delayed duplicate acknowledgement when it refers to a command that has already left the queue head. This prevents a late response from a timed-out attempt from needlessly forcing a reconnect after the next queued command is in flight; the current command remains persisted until its own valid response arrives. Retry backoff also remains exponential across a socket that becomes ready but never returns an authoritative command response; queued sends cannot bypass the scheduled delay, and backoff resets only after a valid response is saved.

The iPhone's iPad-command authority now retries a failed local Network.framework listener with the same capped backoff used by companion command delivery. The retry is cancelled when authority stops or is restarted, and the delay resets after the listener becomes ready.

Watch catalog refresh now checks that a Watch is paired and the Factory Tools Watch app is installed before rebuilding the full counter snapshot. Watch and iPad command acknowledgements already return the changed session, so their receivers no longer trigger duplicate full-catalog rebuilds after the counter service has published the saved update.

The shared Core `CounterCommandOutboxTransaction` now stages new commands and command responses, including unavailable-session cleanup, through a persistence closure before returning the candidate queue. The iPad publishes the returned queue, pending count, and next-send state only after the save succeeds. Core regressions inject save failures for enqueue, ordinary acknowledgement, and unavailable-session cleanup and verify the current queue remains unchanged while the attempted candidate contains the intended update.

The Watch now offers a Japanese/English retry action when its local Outbox cannot be loaded or saved. Retrying rebuilds/reloads the file-store handle and queue without deleting the saved file, then resumes sending the durable head when reachable.

Watch Cycle Time outbox loading rejects malformed and oversized files without rewriting or deleting them. A Core regression test now protects the malformed-file case, so a retry cannot silently turn unreadable queued captures into an empty queue.

Watch command handling now stages the returned session snapshot and queue together: the updated count/catalog and pending count are published only after the acknowledged queue has been saved. Reachability and catalog refresh callbacks also cannot bypass an already scheduled command retry delay.
